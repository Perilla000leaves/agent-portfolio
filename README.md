# agent-portfolio

一个从生产 Agent 系统里剥离出来的工程样本：**语义内核 + Pydantic 入参契约 + 轨迹判定 + 同一链路的三套编排实现**，全部配可运行的回归用例。

## 这个仓库要解决什么问题

跑在框架和内部数据源上的 Agent，代码很难独立验证。最常见的事故不是"算错"，而是**静默失真**：

- 参数传了 `bns_hour="3点-5点"`，解析失败后被当成"不过滤小时"，一次查询扫掉全天分区；
- 媒体名没解析成 `app_id`，SQL 从"查这个媒体"退化成"查全量媒体"；
- 模型声称调用了工具，但实际拿回来的是空的 `functionResponse`。

这三种情况日志里都一切正常，等到有人发现数据不对，已经过去几天。这个仓库把它们拆成可以独立运行、可以断言的东西。

|---|---|---|

| `docs/` | 生产系统的架构取舍、三个工程案例、知识库构建笔记 | — |

## 快速开始

```bash
git clone https://github.com/Perilla000leaves/agent-portfolio.git
cd agent-portfolio
python3 -m venv .venv && ./.venv/bin/pip install -e ".[test,frameworks]"

./.venv/bin/python -m pytest -q      # 73 passed
bash scripts/verify.sh               # 单测 + 三套框架 demo
```

只需要内核、不想装框架依赖：

```bash
pip install -e ".[test]"
```

跨框架用例会自动跳过，内核用例照常运行。

## 三种编排实现

`chaincore/` 里是三个实现共享的**阶段语义**（每个阶段做什么、返回什么），三个目录只回答同一个问题：**下一
步走哪，由谁决定**。

| 目录 | 框架 | 控制流怎么表达 | 分支落在哪 |
|---|---|---|---|
| `langgraph/` | LangGraph | 显式状态图 + 条件边 | 边，编译期定型 |
| `langchain/` | LangChain（LCEL） | `RunnableBranch` | 运行时条件，分支顺序本身即语义 |
| `adk/` | Google ADK | 顺序 Agent + 节点内守卫 | 节点内部 `if` |

因为语义都下沉到 `chaincore`，三个实现可以逐行 diff，差异只有编排。

其中最值得注意的是 ADK：它的 `SequentialAgent` **没有条件边**，分支只能收敛到节点内部判断，或者交给模型
用 `transfer` 决定走哪个子 Agent。这不是实现取舍，是框架表达力的边界，代码里能直接看到。

命名坑：安装的 `langgraph` 是命名空间包（没有 `__init__.py`），仓库里的 `langgraph/` 目录会被并进它的
`__path__`。所以入口文件叫 `chain.py` 而不是 `graph.py`（否则会撞上库的 `langgraph/graph/`），运行也必须
用脚本方式：`python langgraph/chain.py --demo`。

## 参数契约与轨迹判定

两块都是「让不确定的模型输出可被验证」的基础设施，也是这个仓库里最贴近线上事故的两块。

**入参契约（`toolcore/contract.py`）**：Pydantic 模型 + `field_validator`，在调用前拦下
「确定会炸 / 会静默失真」的参数。三条约束写在模块 docstring 里——不改工具签名
（`functools.wraps` 让框架拿到的仍是原始签名，模型看到的说明书一个字不变）、只校验不改写入参、
失败返回 error payload 而不抛异常（抛异常会被框架 re-raise 成整轮 error，模型拿不到可自纠的提示）。

**轨迹判定（`evalcore/`）**：先做**成对归一化**再匹配。期望只写工具名、实际调用带
`bns_date_start` 这类会漂的参数时，严格相等会把对的判成错的；归一化让两侧用同一套规则，
比较才恢复意义。匹配支持 EXACT / IN_ORDER / ANY_ORDER 三种语义，另有两个自建指标：
`query_adx_*` 必须真的上报 SQL（框架的参数比较看不出这一点）、同一工具不得重复调用。

`pass=None` 表示**未判定**，与 `False` 严格区分——把「没测」混进通过率是评测里最常见的自欺。

## 上下文工程

长输入有两个问题：占窗口，而且模型会截断或重写 URL。处理办法不是"提示词要求别改写"，而是
在模型看到之前就把它们换掉。

**整组占位符（`contextcore/`）**：同一轮的所有 URL 收敛成一个标记 `[__URL_LIST__]`（创意 ID 用
`[__CREATIVE_LIST__]`），映射里只有一条「标记 → 逗号拼接的原值」。早期实现用
`[__URL__0]`、`[__URL__1]` 这样的序号，代价是一整套序号状态机——跨轮续接、同值复用、超限裁剪、
按序号反查，还要处理模型"第 N 个"的指代；改成整组后这些全部省掉，代价是不能指代"上一轮第 N 个"。

还原侧必须**宽容**：模型会把标记写成变体（`__url_list__`、多空格、结尾多下划线），
变体一旦穿进工具参数会静默查空——SQL 和 ES 都只把它当普通字符串，比报错更难排查。
所以还原用大小写不敏感的正则，另外单独检测「残留」：还原不干净就**拦下这次调用**让模型重试，
而不是带着占位符去查。还原只作用于工具白名单里的参数，别的参数一个字都不动。

**结果投递**：所有查询结果一律写对象存储返链接，只有行数 ≤ 20 时才额外附一份 HTML 表格给前端。
模型上下文里永远只有「行数 + 列名 + 链接」，表格行不进模型——既不撑爆窗口，模型也没法复述行内容。

## 从代码规则到可检索知识库（RAG）

`ragcore/` 解决一个具体问题：业务规则写在代码里（Python 字面量 + 配置文件 + 线上缓存），
想让它可检索，既不能 `import` 那份代码，也不能把 `lambda` 表达式直接喂给模型。

| 阶段 | 做什么 | 为什么这么做 |
|---|---|---|
| 规则提取 | `ast.parse` 取规则列表里的字面量 | 导入规则模块会连缓存、拉词表、建自动机 |
| 角色推断 | 从 `not (…)` / `A - {…}` / 三元推断 扣除 / 否决 / 开关 | 同一个词在不同标签里可能是反例，不能一律算占用 |
| 分块编译 | 代表词 + 词表续块，按字符预算切分，块首写分隔标记 | 超长词表会静默截断，续块保证不丢词 |
| 频率统计 | 反算每个词被多少个标签使用，只计触发词 | 「被几个标签复用」是治理决策的核心数字 |

`compile_chunks` 的每块都带 `words` 字段，`chunk_word_coverage` 断言编译没丢词——
把「悄悄少一个词」变成构建失败。

切片策略与踩过的坑见 [`docs/rag-notes.md`](docs/rag-notes.md)。

## 测试在守护什么

| 组 | 条数 | 覆盖 |
|---|---|---|
| 参数契约 | 11 | Pydantic 校验器：非数字 id、坏小时、非法日期、非法 source、非法 stage、未知字段、空筛选；合法参数原样放行、失败不执行函数体、错误预览只进 state |
| 时间与字段 | 6 | 分钟窗口、多小时展开、跨小时区间、单日折叠、字段别名补 ts、日期格式兼容 |
| SQL / 摘要 / MIME | 6 | 空 IN、引号与反斜杠转义、分钟分区条件、HTML 表格摘要、超长截断、图片魔数 |
| 轨迹判定 | 14 | 成对归一化（keys / full）、EXACT / IN_ORDER / ANY_ORDER、重复调用、SQL 上报、未判定与失败严格区分 |
| 上下文工程 | 15 | 整组占位符（含变体还原与老序号残留拦截）、只还原白名单参数、映射缺失时拦下而不是放行、结果投递策略 |
| 跨框架一致 | 4 | 三个场景 × 三种编排，输出必须逐字段相同；挂起场景必须真的挂起 |
| 知识库构建 | 17 | 只解析不执行、通道被引用才导出词、四类词角色推断、分块不丢词、df 只计触发词 |

跨框架那 4 条是这个仓库的核心断言：`status / route / creatives / merged / message` 在三个实现之间必须完全
一致。任何一处控制流写错——`RunnableBranch` 分支顺序颠倒、ADK 守卫漏判——都会在这里失败。

用例刻意只写 73 条而不追求覆盖率：测的是会静默出错的地方，不是代码行。

## 设计取舍

- **失败返回字符串而不是抛异常**：模型能从可读错误里自我修正；抛异常会让整轮对话变成 error。
- **结果分两个读者**：模型只看「行数 + 列名 + 下载链接」，前端拿完整表格。表格进上下文既费 token，也会被模型复述。
- **挂起用状态而不是阻塞**：长查询提交后立即返回，进度和结果落对象存储，前端轮询，服务重启后可续跑。
- **三套实现共享语义**：如果每套各写一份业务逻辑，对比就失去了意义——差异会被业务代码淹没。

## 范围与限制

- 数据源是固定样本，验证的是编排语义与参数契约，**不代表真实查询性能**。
- 三个实现都没有接入真实模型：ADK 版用 `SequentialAgent` 跑确定性阶段，对照点是执行模型本身，不是推理质量。
- LangGraph 版**没有使用 checkpointer 与 `interrupt()`**：挂起是用状态标志模拟的，不是持久化中断恢复。这是已知的下一步。
- ADK 2.15 中 `SequentialAgent` 已标记 deprecated（官方建议迁移到 `Workflow`，当前版本尚未完全可用）。
- `docs/` 里的架构与案例来自一个真实生产系统，已省略内部服务地址、模块名与业务数据。
- `toolcore` 依赖 pydantic（生产实现用同一套校验器）；`chaincore`、`evalcore`、`ragcore`、`contextcore` 仍只依赖标准库。
- **不在覆盖范围内**：回调链的编排（`before_model` 三段接力）、上传附件的解析与注入、埋点与运行时上下文——这三块都要跑在具体框架的 callback 生命周期里，抽出来只能靠 mock，反而验证不了什么。本仓库只覆盖它们背后的**纯语义**（占位符怎么换、结果怎么投递、参数怎么校验）。
