# 面试笔记：3 个 STAR + 框架边界

## STAR 1｜50 万行结果把服务打 OOM

**S**：ODPS 曝光明细单次可达 50 万行。旧实现把 `rows`、`DataFrame`、`csv_text` 三份同时驻留，线上一次大查询内存冲到约 5.8GB，8888 服务被拖挂。

**T**：不砍功能、不丢结果，把内存压到常数级。

**A**：
- 读侧改成 `open_reader(limit=False)` 的逐行生成器，调用方写临时 CSV；
- 小结果（≤20 行）才读回内存生成 HTML 预览，大结果直接分片上传 OSS；
- 丢弃全量 list / DataFrame / 拼接字符串；
- 顺带排掉一个坑：`open_reader(limit=N)` 会触发服务端受限读取（实测只回 1 万条），改为客户端计数 + SQL `LIMIT` 双边界。

**R**：内存从 GB 级降到「单行 + 一个分片缓冲」；50 万行可稳定返回；前端预览与下载体验不变。

**可能被追问**：为什么不用 pandas `chunksize`？→ 仍然要拼 DataFrame，且列类型推断会吃掉内存；流式 CSV 更直接。失败重试怎么办？→ 从 InstanceID 重读是幂等的。

## STAR 2｜900 秒硬上限下的长查询与断流恢复

**S**：veFaaS 单请求 900 秒，ODPS 多日明细常跑几十分钟；用户刷新页面、服务重启都会丢进度。

**T**：让长查询「提交即返回」，可轮询、可恢复、多日可合并。

**A**：
- `submit_only` 只在网页会话（有 `progress_key`）生效；提交后把 InstanceID / LogView / SQL 写进 OSS 进度文件；
- 前端 8 秒节流轮询、15 秒心跳；完成后按 InstanceID 重新读结果，不依赖原进程；
- 多日查询按天拆成独立 Instance，父进度记录 subtasks，部分失败保留成功结果并列出失败日期；
- 提交模式下「老区间 + 今天」折叠为一次全范围提交——一个进度 key 同时只跟踪一个实例。

**R**：单请求从「等查询」变「秒级提交」；刷新/重启后仍能补齐结果；多日查询可部分成功。

**可能被追问**：两个提交竞争同一个 key？→ 状态机 + 折叠策略；进度文件写失败？→ 工具内部直接写（不依赖回调链），失败只记日志不影响查询。

## STAR 3｜口径漂移：提示词说 A、工具做 B

**S**：历史上工具归属有三份手工名单（TOOL_META / TOOL_FIELD_META / 回显名单），各自漏项；提示词里的映射表与工具实际职责不一致；媒体名没解析成 app_id 时，SQL 静默退化成全媒体（线上 2026-11-04 真实案例）。

**T**：让口径只有一个事实源，并且**能被测试抓住**。

**A**：
- registry 把三份名单合并为 `TOOL_SPECS`，`tools_for(agent)` 只从这里取；导入时校验「注册表 ↔ 白名单 ↔ 实现」三方一致，不一致直接抛错；
- 工具职责从 docstring 移到提示词单一处（docstring 只留参数说明）；
- 契约层先拦脏参数（非数字 id、坏小时、非法日期、未知字段、空筛选），返回可自纠的 error；
- 名称解析失败时**显式清空** app_id/place_id 并记录未解析名称，后续明细缺 id 时拦截，而不是带着旧值静默收窄。

**R**：新增工具漏注册从「线上才发现」变成「导入即报错」；路由表与职责同步有测试兜底；同类「静默丢条件」事故不再复现。

**可能被追问**：为什么不用文档同步解决？→ 文档没有执行权；只有代码断言能在合并前失败。

# ADK vs LangGraph：为什么选 ADK，边界在哪

## 选 ADK 的理由

1. **多 Agent + 原生 HITL**：`transfer`、`request_confirmation`、`skip_summarization` 都是框架能力，不用自己搭；
2. **回调链**：before/after model/tool 能覆盖「守卫、确认、进度、回显」四类横切逻辑；
3. **部署**：AgentKit Runtime 直接打包，鉴权、扩缩容、日志托管；
4. **工具 schema**：docstring 直接作为模型可见的 description，写文档即写接口。

## LangGraph 更强的地方

1. **显式状态机**：节点/边/条件路由都在代码里，确定性流程不会「模型想走哪走哪」；
2. **可中断与重放**：checkpointer 让「暂停—人工—恢复」变成原生语义；
3. **可视化与调试**：图结构一眼看清分支；
4. **生态**：LangSmith 追踪、大量现成 pattern。

## 边界判断（面试可直接说）

| 场景 | 更适合 |
|---|---|
| 开放式多轮、工具 30+、需要模型自主选择 | ADK 的 agent loop |
| 流程确定、分支明确、需要审计与重放 | LangGraph / ADK 2.x Workflow |
| 长任务、需要暂停等人工 | 两者都可；LangGraph 的 interrupt 更成熟 |
| 已有 AgentKit 部署与鉴权 | ADK，换框架要重建部署链路 |

**结论**：不是二选一。ADK 负责「理解与编排」，图工作流负责「确定性收尾」；`adk/`、`langchain/`、`langgraph/` 三个目录就是把一条确定性链路（素材→创意→落地页→合并）各实现一次，用来验证「同一业务语义在三种编排模型下怎么表达」，并由一致性用例守住语义不漂移。
