# 三个工程案例

来自同一个生产 Agent 系统的三次真实故障与改造。每个案例按**问题 / 约束 / 决策 / 结果 / 权衡**组织，
保留的是判断过程，不是结论本身。

---

## 案例一：50 万行结果把服务打 OOM

**问题**
ODPS 曝光明细单次可达 50 万行。旧实现把 `rows`、`DataFrame`、`csv_text` 三份数据同时驻留内存，
一次大查询使内存冲到约 5.8GB，业务工作台被拖挂。

**约束**
不砍功能、不丢结果——业务方需要完整明细用于对账，只是不需要在服务端展开。

**决策**
- 读侧改成逐行生成器，调用方直接写临时 CSV，不再构造 DataFrame；
- 只有小结果（≤20 行）才读回内存生成 HTML 预览，大结果分片上传对象存储；
- 丢弃全量 list、DataFrame 和拼接字符串三份冗余视图；
- 顺带排掉一个坑：`open_reader(limit=N)` 会触发服务端受限读取，实测只回 1 万条，
  改为客户端计数 + SQL `LIMIT` 双边界。

**结果**
内存从 GB 级降到「单行 + 一个分片缓冲」；50 万行可稳定返回；前端预览与下载体验不变。

**权衡**
为什么不用 pandas 的 `chunksize`？它仍然要拼 DataFrame，且列类型推断本身吃内存；流式 CSV 更直接。
失败重试怎么办？从实例 ID 重新读取是幂等的，重试不需要额外去重逻辑。

## 案例二：900 秒硬上限下的长查询与断流恢复

**问题**
托管运行时单请求上限 900 秒，而 ODPS 多日明细常跑几十分钟。用户刷新页面、服务重启都会丢进度。

**约束**
不能改运行时限制，只能在协议层把「等查询」拆成「提交 + 轮询」。

**决策**
- `submit_only` 只在网页会话（有进度 key）生效：提交后把实例 ID、LogView、SQL 写进对象存储的进度文件；
- 前端 8 秒节流轮询、15 秒心跳；完成后按实例 ID 重新读结果，不依赖原进程存活；
- 多日查询按天拆成独立实例，父进度记录子任务，部分失败保留成功结果并列出失败日期；
- 提交模式下「老区间 + 今天」折叠为一次全范围提交——一个进度 key 同时只跟踪一个实例。

**结果**
单请求从「等查询」变「秒级提交」；刷新或重启后仍能补齐结果；多日查询支持部分成功。

**权衡**
两个提交竞争同一个进度 key？用状态机加折叠策略解决。进度文件写失败？工具内部直接写、不依赖回调链，
失败只记日志不影响查询主流程。

## 案例三：口径漂移——提示词说 A，工具做 B

**问题**
工具归属曾有三份手工名单（工具元数据、字段元数据、回显名单），各自漏项；提示词里的映射表与工具实际
职责不一致；媒体名没解析成 `app_id` 时，SQL 静默退化成全媒体查询。

**约束**
文档没有执行权。只有代码断言能在合并前失败，所以「统一口径」必须落在代码里。

**决策**
- registry 把三份名单合并为一份工具规格表，`tools_for(agent)` 只从这里取；
- 导入时校验「注册表 ↔ 权限白名单 ↔ 实现」三方一致，不一致直接抛错；
- 工具职责从 docstring 移到提示词单一处，docstring 只留参数说明；
- 契约层先拦脏参数（非数字 id、坏小时、非法日期、未知字段、空筛选），返回可自纠的 error；
- 名称解析失败时**显式清空** `app_id` / `place_id` 并记录未解析名称，后续明细缺 id 时拦截，
  而不是带着旧值静默收窄。

**结果**
新增工具漏注册从「线上才发现」变成「导入即报错」；路由表与职责不同步有测试兜底；同类静默丢条件的事故
不再复现。

**权衡**
为什么不用文档同步解决？因为文档没有执行权。这一条也解释了本仓库为什么把契约和用例放在一起：
能被 CI 执行的断言，才是真正的口径。

# 框架选型：ADK 与图编排的边界

## 选 ADK 的原因

1. **多 Agent + 原生人工介入**：`transfer`、`request_confirmation`、`skip_summarization` 都是框架能力；
2. **回调链**：before/after model/tool 能覆盖「守卫、确认、进度、回显」四类横切逻辑；
3. **部署**：托管运行时直接打包，鉴权、扩缩容、日志托管；
4. **工具 schema**：docstring 直接作为模型可见的 description，写文档即写接口。

## 图编排更强的地方

1. **显式状态机**：节点、边、条件路由都在代码里，确定性流程不会被模型随意带偏；
2. **可中断与重放**：checkpointer 让「暂停—人工—恢复」成为原生语义；
3. **可视化**：图结构一眼看清分支；
4. **生态**：追踪与现成 pattern 更多。

## 边界判断

| 场景 | 更适合 |
|---|---|
| 开放式多轮、工具 30+、需要模型自主选择 | ADK 的 agent loop |
| 流程确定、分支明确、需要审计与重放 | LangGraph 或 ADK 的 Workflow |
| 长任务、需要暂停等人工 | 两者都可；LangGraph 的 interrupt 更成熟 |
| 已有托管部署与鉴权 | ADK，换框架要重建部署链路 |

结论不是二选一：ADK 负责理解与编排，图工作流负责确定性收尾。本仓库的 `adk/`、`langchain/`、`langgraph/`
三个目录，就是把这个结论变成可运行、可 diff 的代码——同一条链路，三种控制流表达，输出必须一致。
